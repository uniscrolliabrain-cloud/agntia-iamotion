# M1 — Integridad, identidad y evidencia
Plan exclusivamente documental. Entradas actuales: library/catalog/assets.json, semantic.json, inventory/{main,ui-lab,ui-lab-pro}.json, taxonomy/lexicon.v1.json, entities/* y recibo entity-build.json.
## P01 — Auditoría de almacenamiento
Crear lab/scripts/audit-baseline.mjs y fixtures. Leer JSON con límite de bytes, validar estructura antes de recorrer. Construir mapa hash->rutas y mapa repo/commit/path->hash. Verificar cada archivo local por streaming SHA256, tamaño, magic bytes y ruta real contenida; rechazar symlinks, LFS pointer, SVG con scripts o referencias externas. No abrir imágenes mediante navegador. Emitir audit.json con missing, mismatch, unsafe, duplicate, orphan y counts. No copiar ni borrar. Exit 2 si integridad falla, 0 si solo hay pendientes declarados.
## P02 — Separación de datos
Conservar library/entities actuales como snapshot legado. Nuevo layout library/generated/<snapshotId>/binary/, library/reviews/append-only/, library/catalog/current.json. SnapshotId = hash de manifiesto canónico sin timestamps. El puntero current solo cambia tras validación; las revisiones nunca se escriben desde generadores. Migración dry-run produce mapa de rutas y hashes; no mover hasta aprobación.
## P03 — Contratos
Crear src/factory/assets/schemas/{binary,visual,evidence,claim,review,relation}.ts, export barrel y JSON Schema generado. IDs: binary sha256 minúscula; visual v_<UUID asignado y persistido>; claim c_<hash de entidad,predicado,valor,evidencia,basis>; review r_<UUID>. Strict object, arrays acotados, strings UTF8 con límite; rechazar claves desconocidas. Revisión referencia versión exacta y actor autorizado por host. Scope público de plataforma por defecto únicamente para fuentes aprobadas; unknown no equivale a public.
## P04 — Ontología
Migrar 115 términos sin cambiar IDs. Cada término tiene label.es/en, definition.es/en, aliases por idioma, facet, parentId nullable, status, replacementId nullable. Validar unicidad, DAG y reemplazos sin ciclos. Alias ambiguo devuelve conjunto de candidatos, no gana por orden de inserción. Introducir facetas identity y learning explícitas y distinguir subject.photo de style.photographic.
## P05 — Reconciliación
Resolver tarjetas por hash declarado o ruta fijada al commit. Si ambos existen y discrepan, emitir conflict. Crear visualId solo mediante registro persistente; candidatos de agrupación por manifiesto explícito. Mantener relaciones binary->visual y visual->binary; no asumir cardinalidad 1:1. Las 14 tarjetas sin enlace siguen visibles como pendientes. Nunca fusionar por basename.
## P06 — Evidencia
Normalizar claims actuales preservando matchedPhrase y fuente. Un claim de intención no pasa a observed. Crear ledger de revisiones con supersedes y expectedRevision; detectar conflicto concurrente. Resolver vista efectiva por decisión explícita, no por timestamp más reciente. Exportar cobertura por facet/basis/status.
## Fixtures y gates
F01 hash corrupto; F02 ruta ../; F03 dos archivos mismo basename; F04 manifiesto contradice hash; F05 alias polisémico; F06 ciclo de taxonomía; F07 revisión antigua; F08 claim sin evidencia; F09 mismo input dos ejecuciones. Esperado: F01-08 rechazados o conflicto explícito; F09 mismo hash. Baseline 403/166/206 no debe perderse sin explicación. Rollback: conservar puntero previo y ledger intacto.
